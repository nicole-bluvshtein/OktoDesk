# OktoDesk — מערכת לניהול טיקטים וקריאות שירות ארגוניות

---

## תיאור הבעיה העסקית

בארגונות רבים, פניות עובדים לתמיכה טכנית מנוהלות בצורה לא סדורה:  
הודעות אישיות בווטסאפ או בסלאק, קבצי אקסל מאולתרים, טפסי Google Form שאינם מחוברים לשום מעקב מרכזי.  
כתוצאה מכך, פניות נופלות בין הכסאות, לא נענות בזמן, ואין שום אפשרות לעמוד ביעדי SLA או לנתח מגמות.

**OktoDesk** באה לפתור את הבעיה הזו: מערכת ארגונית פנימית לניהול מרכזי של קריאות שירות, שמבטיחה מענה מסודר, תיעוד מלא, תעדוף חכם ושמירה על יעדי זמן התגובה.

---

## משתמשי המערכת

| משתמש | תיאור | הרשאות עיקריות |
|---|---|---|
| **עובד ארגוני** | כל עובד בארגון שצריך תמיכה טכנית | פתיחת טיקטים, צפייה בטיקטים שלו |
| **טכנאי IT** | מטפל בקריאות השירות | צפייה, עריכה וסגירת טיקטים, תיעוד פתרונות |
| **מנהל IT** | אחראי על צוות התמיכה | כל הרשאות הטכנאי + הפקת דוח SLA ועומס עבודה וייצוא שלו |

> **הערה:** טכנאי ומנהל IT הם גם עובדים ארגוניים — הם נמצאים בהיררכיית ירושה מעל העובד הבסיסי, עם הרשאות מורחבות.

## תהליכים מרכזיים

### 1. פתיחת קריאת שירות (על ידי עובד)
1. העובד נכנס למערכת ופותח טופס חדש.
2. ממלא פרטים: **כותרת**, **תיאור הבעיה**, **קטגוריה** ו**רמת דחיפות**.
3. המערכת יוצרת רשומת טיקט חדשה עם:
   - מזהה ייחודי אוטומטי
   - תאריך ושעת פתיחה
   - שיוך לעובד הפותח
   - סטטוס התחלתי: `פתוח`
4. הטיקט מתווסף לתור הטיקטים הפתוחים ממוין לפי דחיפות.

### 2. טיפול בקריאת שירות (על ידי טכנאי)
1. הטכנאי צופה ברשימת הטיקטים הפתוחים הממוינת לפי דחיפות.
2. בוחר טיקט ומשנה את הסטטוס ל-`בטיפול`.
3. במהלך הטיפול, הטכנאי יכול לעדכן: **סטטוס**, **דחיפות**, **נושא** ו**תוכן**.
4. כל פעולת עדכון נשמרת ביומן הפעילות של הטיקט (Log) עם חותמת זמן.
5. עם סיום הטיפול — הטכנאי מתעד את **הפתרון** וסוגר את הטיקט.

### 3. סגירת טיקט ותיעוד פתרון
1. הטכנאי ממלא שדה **תיאור הפתרון**.
2. הטיקט מועבר לרשימת הטיקטים הסגורים (לא מוצג בתצוגה הפעילה).
3. הפתרון נשמר גם ב-**Knowledge Base** (מאגר הפתרונות) לשימוש עתידי.

### 4. Knowledge Base — מאגר פתרונות
1. בעת סגירת טיקט, המערכת שומרת את הפתרון כרשומת ידע חדשה.
2. טכנאים יכולים לחפש במאגר לפי מילות מפתח וקטגוריה.
3. ניתן לקשר טיקטים פתוחים לפתרונות קיימים.

### 5. דוחות ומעקב SLA (על ידי מנהל IT)
1. המנהל מפיק דוח SLA ועומס עבודה: אילו טיקטים פתוחים חרגו מיעד ה-SLA ובכמה שעות, וכמה טיקטים פתוחים יש לכל טכנאי.
2. המערכת מחשבת אוטומטית עמידה ביעדי SLA לפי דחיפות הטיקט.
3. רק מנהל IT בעל הרשאת ייצוא (`can_export_reports`) יכול לייצא את הדוח; ניסיון של משתמש אחר נדחה.

## קשרים בין ישויות

```
User ──────────── פותח ──────────────> Ticket
Technician ─────── מטפל ─────────────> Ticket
Ticket ──────────── שייך לו ──────────> Status
Ticket ──────────── שייך לו ──────────> Priority
Ticket ──────────── מכיל ─────────────> ActivityLog (entries)
Ticket ──────────── מייצר (בסגירה) ──> KnowledgeBaseEntry
ITManager ─────────── מנהל ────────────> Technician[]
```

- **Technician יורש מ-User** — טכנאי הוא גם עובד בארגון עם הרשאות מורחבות.
- **ITManager יורש מ-Technician** — מנהל IT הוא גם טכנאי עם הרשאות ניהוליות נוספות.
- **קריאת שירות** שייכת לעובד אחד (פותח) ויכולה להיות משויכת לטכנאי אחד (מטפל).
- **Status ו-Priority** הן ישויות ערך (Value Objects) השייכות לטיקט.
- **KnowledgeBaseEntry** נוצרת אוטומטית מהטיקט בעת סגירה, אך קיימת כישות עצמאית לאחר מכן.

## מימוש ה-OOP — הרכבה, ירושה ופולימורפיזם

מומש ב-`oktodesk/models.py`.

### הרכבה (Composition)

`Ticket` "מכיל" את `activity_log` שלו — רשימת רשומות פעילות שאין להן משמעות
עצמאית מחוץ לטיקט שהן שייכות אליו (יחס has-a אמיתי). שתי פעולות חושפות את
היומן הזה:

- `add_log_entry(performed_by, action)` — מוסיפה רשומה חדשה עם חותמת זמן.
- `activity_summary()` — סופרת כמה פעולות ביצע כל גורם (`performed_by`),
  באמצעות `counts.get(performed_by, 0) + 1` כדי לספור גם גורם שמופיע לראשונה
  ביומן בלי לזרוק שגיאה.

### ירושה ופולימורפיזם

ההיררכיה: `User` (בסיס) ← `Technician(User)` ← `ITManager(Technician)`.

כל מחלקה דורסת (`override`) את `describe_capabilities()`, וכל דריסה קוראת
ל-`super().describe_capabilities()` ומוסיפה את היכולות הייחודיות לה — כך
שהיכולות "נערמות" ככל שיורדים במדרג הירושה. ב-`main.py` מודגם הפולימורפיזם
על ידי איטרציה על רשימה מעורבת (`list[User]`) המכילה גם `User`, גם
`Technician` וגם `ITManager`, וקריאה ל-`.describe_capabilities()` על כל
איבר — בלי אף בדיקת `isinstance()` או `type()` בשום מקום בקוד.

### מחלקה מופשטת (Abstract Class)

`NotificationChannel` היא מחלקה מופשטת (`ABC`) עם מתודה מופשטת אחת:
`notify(ticket, message)`. Python מונע לחלוטין יצירת מופע ישיר של
`NotificationChannel` — ניסיון כזה זורק `TypeError`. שתי תת-מחלקות קונקרטיות,
`EmailNotificationChannel` ו-`SlackNotificationChannel`, ממשות את `notify()`
בפועל (כרגע כ-`print` בלבד, ללא שליחה אמיתית).

### עטיפה ואימות (Encapsulation & Validation)

- `User.email` הוא property עם setter שבודק תבנית מייל תקינה ברגקס (regex),
  וזורק `ValueError` עם שם השדה שנפסל אם הכתובת אינה תקינה.
- `Ticket.priority` ו-`Ticket.status` הם גם הם properties, ושניהם עוברים דרך
  מתודת בדיקה פרטית משותפת אחת — `_validated_enum_value` — שמוודאת שהערך
  שהתקבל הוא באמת חבר של ה-`Enum` המתאים (`Priority` או `Status`), אחרת
  זורקת `ValueError` ברור. כך אין דרך ליצור טיקט או לשנות אותו למצב לא-תקין.

### כלים נוספים (מעבר ל-`from_dict`)

- `Ticket.sla_target_hours(priority)` — `@staticmethod`, מיפוי טהור בין
  רמת דחיפות ליעד ה-SLA שלה בשעות.
- `Ticket.priority_rank` — property מחושב, ממיר את ה-`Priority` לדירוג
  מספרי (0 = הכי דחוף).
- `Ticket.is_overdue` — property מחושב שבודק אם הטיקט חרג מיעד ה-SLA שלו
  (תמיד `False` עבור טיקט סגור).
- `Ticket.__lt__` — משווה שני טיקטים לפי `(priority_rank, created_at)`,
  ומאפשר להכניס טיקטים ישירות ל-heap של `heapq` בלי מפתח מיון נפרד.

## מבני נתונים ועיבוד קולקציות

### מקור הנתונים ותהליך הטעינה

`data/sample_data.jsonl` מכיל 16 רשומות טיקט סינתטיות שנוצרו בסיוע AI (ראו
פירוט מלא ב-`AI_USAGE.md`) — קובץ JSONL, כלומר אובייקט JSON תקין אחד בכל
שורה. `oktodesk/repository.py` (`load_tickets`) פותח את הקובץ עם
`with open(path, encoding="utf-8") as f:` ועובר על אובייקט הקובץ שורה-שורה
(לעולם לא `.read()` או `.readlines()`), כדי שהטעינה תישאר lazy ולא תדרוש
לטעון את כל הקובץ לזיכרון בבת אחת.

כל שורה עוברת `json.loads` ואז `Ticket.from_dict(...)`, שממיר את המילון
הגולמי לאובייקט `Ticket` אמיתי (כולל המרת מחרוזות ל-`Priority`/`Status`
מתאימים). תהליך האימות לכל שורה:

- שדה חובה חסר, או ערך `priority`/`status` שאינו שם חבר תקין ב-Enum —
  השורה **מדולגת** (`skip`) ומתועדת עם מספר השורה והסיבה, אך הטעינה ממשיכה.
- מזהה טיקט (`ticket_id`) כפול — נחשב לשגיאה חמורה יותר: `load_tickets`
  זורק `ValueError` ועוצר את הטעינה כולה, במקום לדרוס בשקט את הרשומה
  הקיימת באינדקס.

### טבלת מבני הנתונים

| מבנה | היכן נעשה בו שימוש | למה |
|---|---|---|
| `list` | אוסף הטיקטים בזיכרון (`tickets`) | סדור, ניתן למיון מחדש |
| `tuple` | רשומת דילוג בטעינה: `(line_number, reason)` | קצרה, קבועה, לא משתנה |
| `set` | `Technician.expertise_areas`, `category_set(tickets)` | ייחודיות וחברות (`in`) הן העיקר, לא סדר |
| `dict` #1 | `tickets_by_id: dict[int, Ticket]` | חיפוש מהיר לפי מזהה |
| `dict` #2 | `open_ticket_count_by_technician: dict[str, int]` | קיבוץ וספירה |
| `deque` (FIFO) | `notification_queue` | הודעת "טיקט נפתח" יוצאת לפי סדר הגעה |
| `heapq` (Priority Queue) | תור הטיקטים הפתוחים של הטכנאי | הדחיפות גוברת על סדר ההגעה |

### פעולות שמשנות אוסף קיים מול פעולות שיוצרות אוסף חדש

| משנה במקום (mutate in place) | יוצרת אוסף חדש (returns new) |
|---|---|
| `activity_log.append(entry)` | `sorted(tickets, key=...)` |
| `counts[performed_by] = ...` | `{t.category for t in tickets}` (set comprehension) |
| `technician.expertise_areas.add(area)` | `{t.ticket_id: t for t in tickets}` (dict comprehension) |
| `queue.append(...)` / `queue.popleft()` | `[t for t in tickets if t.is_overdue]` (list comprehension) |

## איטרטורים, גנרטורים ו-lazy evaluation

מומש ב-`oktodesk/iterators.py`.

### Iterable / Iterator מותאמים אישית

`TicketCollection` הוא ה-Iterable: מחזיק את רשימת הטיקטים, וכל קריאה ל-`__iter__`
שלו מחזירה **מופע חדש** של `TicketIterator` (Iterator). `TicketIterator` שומר
אינדקס פנימי משלו, מיישם `__iter__` (מחזיר את עצמו) ו-`__next__` (זורק
`StopIteration` כשנגמרים הטיקטים).

בגלל ש-`iter()` בכל פעם בונה `TicketIterator` חדש, שני איטרטורים שנשלפו
מאותו `TicketCollection` הם עצמאיים לחלוטין ולא חולקים מצב — ב-`main.py` זה
מודגם על ידי קידום איטרטור אחד פעמיים (`next()` פעמיים) ואיטרטור שני פעם
אחת בלבד, ושניהם "מפגרים" זה מזה בלי להשפיע אחד על השני.

### גנרטור (`yield`)

`iter_open_tickets(tickets)` הוא פונקציית גנרטור שמחזירה (`yield`) רק טיקטים
שהסטטוס שלהם אינו `סגור`, בעצלנות (lazy) — טיקט אחד בכל פעם, בלי לבנות רשימה
שלמה מראש.

ב-`main.py` מודגם: משיכה ראשונה עם `next()` ידני, המשך עם `for`, ואז מעבר
שני מלא שמראה שהגנרטור הראשון "נגמר" (spent) — יש לבנות גנרטור חדש לחלוטין
(קריאה נוספת ל-`iter_open_tickets(...)`) כדי לעבור על הרשימה מההתחלה.

### הצינור העצלן (Lazy Pipeline) בעל שלושה שלבים

`open_ticket_id_pipeline(tickets, priority)` בונה שלושה ביטויי גנרטור
(generator expressions) מקושרים זה לזה, בלי אף רשימת ביניים:

1. סינון לפי `priority`.
2. סינון לטיקטים פתוחים בלבד (סטטוס שאינו `סגור`).
3. חילוץ `ticket_id`.

ארבע נקודות מרכזיות שמדגימות את ההתנהגות (הדגמה מלאה ב-`main.py`):

- **מה בפועל "מפעיל" את הצינור** — לא בניית הביטוי עצמו, אלא המשיכה
  הראשונה של ערך ממנו (`next()` או איטרציה). עד אז שום טיקט לא נבדק בפועל.
- **אילו טיקטים לא נבדקו בכלל** — כשצורכים רק את שתי התוצאות הראשונות
  (למשל עם `itertools.islice(pipeline, 2)`), המקור (`tickets`) עוצר מוקדם.
  ב-`main.py` זה מודגם עם עוקב (`_tracked_tickets`) שרושם אילו טיקטים בפועל
  נבדקו — ומראה שהטיקטים שמעבר לנקודת העצירה לא נבדקו כלל, גם אם היו
  מתאימים לתנאי הסינון.
- **ההבדל מ-comprehension** — רשימת/קבוצת comprehension (למשל
  `[t for t in tickets if ...]`) היא eager: היא בונה את כל התוצאה בזיכרון
  מראש, לפני שנעשה בה כל שימוש. גנרטור, לעומת זאת, לא מבצע שום עבודה עד
  שממש מבקשים ממנו ערך.
- **מעבר שני על הנתונים** — צריך לבנות ביטוי גנרטור חדש (קריאה נוספת
  לפונקציה), ולא ניתן להשתמש חזרה באותו אובייקט גנרטור שכבר "נצרך" — בדיוק
  כמו הגנרטור הפשוט שלמעלה.

## מנהל הקשר (Context Manager) — `TicketWorkSession`

מומש ב-`oktodesk/context_managers.py`.

`TicketWorkSession(ticket, actor)` עוטף "מפגש עבודה" על טיקט בודד:

- **`__enter__`** — שומר את הסטטוס הנוכחי של הטיקט (`_previous_status`),
  משנה אותו ל-`בטיפול`, מתעד רשומה ביומן הפעילות (`add_log_entry`), ומחזיר
  את הטיקט עצמו (כדי לאפשר `with TicketWorkSession(ticket, actor) as t:`).
- **`__exit__` בסיום תקין** — לא נוגע בסטטוס בכלל, ומשאיר אותו כמו שהקורא
  קבע בתוך בלוק ה-`with` (למשל אם הטכנאי סגר את הטיקט וקבע `status = סגור`).
  רק מתעד רשומת "סיום מפגש" ביומן.
- **`__exit__` כשקורה חריגה בתוך הבלוק** — משחזר את הסטטוס שנשמר
  ב-`__enter__` (כלומר "מבטל" את המעבר ל-`בטיפול`), מתעד ביומן שהמפגש נכשל
  כולל תיאור השגיאה, ומחזיר `False` — כך שהחריגה ממשיכה להתפשט (`propagate`)
  אל הקוד שקרא ל-`with` ולא "נבלעת" בשקט.

ב-`main.py` מודגמות שתי הרצות: מפגש רגיל שסוגר טיקט עם פתרון (הסטטוס נשאר
כמו שנקבע בתוך הבלוק), ומפגש שבו נזרקת חריגה בכוונה (הסטטוס חוזר בדיוק למה
שהיה לפני תחילת המפגש).

## הוראות הרצה

דורש **Python 3.10 ומעלה**. התלות החיצונית היחידה היא `requests` (לפנייה לשירות
החיצוני); `pytest` משמש להרצת הבדיקות.

```bash
# יצירת סביבה וירטואלית
# macOS / Linux:
python3 -m venv .venv
# Windows:
py -3 -m venv .venv

# הפעלת הסביבה
# macOS / Linux:
source .venv/bin/activate
# Windows (PowerShell):
.venv\Scripts\Activate.ps1

# התקנת התלויות
pip install requests "pytest>=8.0"

# הרצת התוכנית
python main.py

# הרצת הבדיקות
python -m pytest -v
```

> **הערה (Windows):** חלק מהנתונים בתוך `data/sample_data.jsonl` וטקסטי
> התצוגה של `Status`/`Priority` הם בעברית. אם מסוף Windows (PowerShell/cmd)
> זורק `UnicodeEncodeError` בזמן ההדפסה, יש להריץ עם קידוד UTF-8 מפורש:
> `py -X utf8 main.py`.

התוכנית מריצה ברצף אחד את כל ההדגמות: טעינת הנתונים מ-`data/sample_data.jsonl`,
מודל ה-OOP, מבני הנתונים והמיון, תור FIFO ותור עדיפויות (`heapq`), האיטרטורים
והגנרטורים, הצינור העצלן, ומנהל ההקשר.
