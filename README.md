# OktoDesk — מערכת לניהול טיקטים וקריאות שירות ארגוניות

---

## תיאור הבעיה העסקית

בארגונות רבים, פניות עובדים לתמיכה טכנית מנוהלות בצורה לא סדורה:  
הודעות אישיות בווטסאפ או בסלאק, קבצי אקסל מאולתרים, טפסי Google Form שאינם מחוברים לשום מעקב מרכזי.  
כתוצאה מכך, פניות נופלות בין הכסאות, לא נענות בזמן, ואין שום אפשרות לעמוד ביעדי SLA או לנתח מגמות.

**OktoDesk** באה לפתור את הבעיה הזו: מערכת ארגונית פנימית לניהול מרכזי של קריאות שירות, שמבטיחה מענה מסודר, תיעוד מלא, תעדוף חכם ושמירה על יעדי זמן התגובה.

---

## משתמשי המערכת

| משתמש | תיאור | הרשאות עיקריות |
|---|---|---|
| **עובד ארגוני** | כל עובד בארגון שצריך תמיכה טכנית | פתיחת טיקטים, צפייה בטיקטים שלו |
| **טכנאי IT** | מטפל בקריאות השירות | צפייה, עריכה וסגירת טיקטים, תיעוד פתרונות |
| **מנהל IT** | אחראי על צוות התמיכה | כל הרשאות הטכנאי + צפייה בדוחות, מעקב SLA, ניהול משתמשים |

> **הערה:** טכנאי ומנהל IT הם גם עובדים ארגוניים — הם נמצאים בהיררכיית ירושה מעל העובד הבסיסי, עם הרשאות מורחבות.

---

## תהליכים מרכזיים

### 1. פתיחת קריאת שירות (על ידי עובד)
1. העובד נכנס למערכת ופותח טופס חדש.
2. ממלא פרטים: **כותרת**, **תיאור הבעיה**, **קטגוריה** ו**רמת דחיפות**.
3. המערכת יוצרת רשומת טיקט חדשה עם:
   - מזהה ייחודי אוטומטי
   - תאריך ושעת פתיחה
   - שיוך לעובד הפותח
   - סטטוס התחלתי: `פתוח`
4. הטיקט מתווסף לתור הטיקטים הפתוחים ממוין לפי דחיפות.

### 2. טיפול בקריאת שירות (על ידי טכנאי)
1. הטכנאי צופה ברשימת הטיקטים הפתוחים הממוינת לפי דחיפות.
2. בוחר טיקט ומשנה את הסטטוס ל-`בטיפול`.
3. במהלך הטיפול, הטכנאי יכול לעדכן: **סטטוס**, **דחיפות**, **נושא** ו**תוכן**.
4. כל פעולת עדכון נשמרת ביומן הפעילות של הטיקט (Log) עם חותמת זמן.
5. עם סיום הטיפול — הטכנאי מתעד את **הפתרון** וסוגר את הטיקט.

### 3. סגירת טיקט ותיעוד פתרון
1. הטכנאי ממלא שדה **תיאור הפתרון**.
2. הטיקט מועבר לרשימת הטיקטים הסגורים (לא מוצג בתצוגה הפעילה).
3. הפתרון נשמר גם ב-**Knowledge Base** (מאגר הפתרונות) לשימוש עתידי.

### 4. Knowledge Base — מאגר פתרונות
1. בעת סגירת טיקט, המערכת שומרת את הפתרון כרשומת ידע חדשה.
2. טכנאים יכולים לחפש במאגר לפי מילות מפתח וקטגוריה.
3. ניתן לקשר טיקטים פתוחים לפתרונות קיימים.

### 5. דוחות ומעקב SLA (על ידי מנהל IT)
1. המנהל צופה בלוח בקרה עם נתונים שוטפים.
2. המערכת מחשבת אוטומטית עמידה ביעדי SLA לפי דחיפות הטיקט.
3. ניתן לייצא דוחות עם נתוני ביצועים, תקלות חוזרות ועומס עבודה.

## ישויות המערכת

### `User` — משתמש ארגוני
| שדה | תיאור |
|---|---|
| `user_id` | מזהה ייחודי |
| `name` | שם מלא |
| `email` | כתובת מייל |
| `department` | מחלקה |
| `role` | תפקיד (`employee` / `technician` / `it_manager`) |

### `Technician` (יורש מ-`User`) — טכנאי IT
| שדה | תיאור |
|---|---|
| `technician_id` | מזהה ייחודי לטכנאי |
| `assigned_tickets` | רשימת טיקטים בטיפולו |
| `expertise_areas` | תחומי התמחות |

### `ITManager` (יורש מ-`Technician`) — מנהל IT
| שדה | תיאור |
|---|---|
| `managed_technicians` | רשימת הטכנאים תחת ניהולו |
| `can_export_reports` | הרשאת ייצוא דוחות |

### `Ticket` — קריאת שירות
| שדה | תיאור |
|---|---|
| `ticket_id` | מזהה ייחודי |
| `title` | כותרת הקריאה |
| `description` | תיאור מפורט |
| `category` | קטגוריה (חומרה / תוכנה / רשת וכו') |
| `priority` | דחיפות (ראה ישות `Priority`) |
| `status` | סטטוס נוכחי (ראה ישות `Status`) |
| `opened_by` | שיוך לעובד שפתח |
| `assigned_to` | שיוך לטכנאי מטפל |
| `created_at` | תאריך ושעת פתיחה |
| `updated_at` | תאריך ושעת עדכון אחרון |
| `closed_at` | תאריך ושעת סגירה |
| `solution` | תיאור הפתרון (בעת סגירה) |
| `activity_log` | יומן כל הפעולות שבוצעו על הטיקט |

### `Status` — סטטוס קריאה
| ערך | משמעות |
|---|---|
| `פתוח` | הטיקט נפתח, ממתין לטיפול |
| `בטיפול` | טכנאי לקח בעלות |
| `ממתין למידע` | הטיקט עצר — ממתין לתגובה מהעובד |
| `סגור` | הטיקט טופל ונסגר |

### `Priority` — דחיפות קריאה
| ערך | משמעות | יעד SLA |
|---|---|---|
| `קריטי` | השבתה מלאה, משפיע על ייצור | 1 שעה |
| `גבוה` | פגיעה משמעותית בעבודה | 4 שעות |
| `בינוני` | מגבלה חלקית בעבודה | 8 שעות |
| `נמוך` | אי נוחות, ניתן להמתין | 24 שעות |

### `KnowledgeBaseEntry` — רשומת ידע
| שדה | תיאור |
|---|---|
| `entry_id` | מזהה ייחודי |
| `title` | כותרת הפתרון |
| `problem_description` | תיאור הבעיה |
| `solution_description` | תיאור הפתרון |
| `category` | קטגוריה |
| `keywords` | מילות מפתח לחיפוש |
| `source_ticket_id` | מזהה הטיקט שממנו נגזר הפתרון |
| `created_at` | תאריך יצירה |

## קשרים בין ישויות

```
User ──────────── פותח ──────────────> Ticket
Technician ─────── מטפל ─────────────> Ticket
Ticket ──────────── שייך לו ──────────> Status
Ticket ──────────── שייך לו ──────────> Priority
Ticket ──────────── מכיל ─────────────> ActivityLog (entries)
Ticket ──────────── מייצר (בסגירה) ──> KnowledgeBaseEntry
ITManager ─────────── מנהל ────────────> Technician[]
```

- **Technician יורש מ-User** — טכנאי הוא גם עובד בארגון עם הרשאות מורחבות.
- **ITManager יורש מ-Technician** — מנהל IT הוא גם טכנאי עם הרשאות ניהוליות נוספות.
- **קריאת שירות** שייכת לעובד אחד (פותח) ויכולה להיות משויכת לטכנאי אחד (מטפל).
- **Status ו-Priority** הן ישויות ערך (Value Objects) השייכות לטיקט.
- **KnowledgeBaseEntry** נוצרת אוטומטית מהטיקט בעת סגירה, אך קיימת כישות עצמאית לאחר מכן.

## זרימת מידע

```
[עובד] ──פותח טפסת─→ [Ticket חדש]
                          │
                    [תור ממוין לפי Priority]
                          │
               [טכנאי צופה ובוחר טיקט]
                          │
                  [Ticket: סטטוס → בטיפול]
                          │
                 [Activity Log מתעדכן]
                          │
              [טכנאי מסיים ומתעד פתרון]
                          │
               ┌──────────┴──────────┐
               ↓                     ↓
    [Ticket → סגור]       [KnowledgeBaseEntry חדשה]
    [מועבר לארכיון]       [נשמרת ב-Knowledge Base]
               │
     [מנהל IT → דוחות + מעקב SLA]
```

## ערך עסקי

| בעיה היום | פתרון ב-OktoDesk |
|---|---|
| פניות נופלות בין הכסאות | מרכוז כל הפניות במקום אחד עם מזהה ייחודי |
| אין מעקב אחר זמני טיפול | תיעוד חותמת זמן בכל שלב + חישוב SLA אוטומטי |
| תעדוף מבוסס זמינות בלבד | תעדוף מובנה לפי דחיפות |
| אין תיעוד היסטוריית עבודה | Activity Log מלא לכל טיקט |
| אין למידה מתקלות עבר | Knowledge Base מרכזית לפתרונות |
| אין נראות למנהל | לוח בקרה + דוחות ייצוא למנהל IT |

**מטרה עסקית מרכזית:** מתן שירות מהיר, איכותי ויעיל לעובדי הארגון, הבטחת מענה מסודר לכל פנייה, מניעת השבתות ממושכות ושיפור שביעות הרצון הארגונית.
